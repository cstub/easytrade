## 1. Source inspection - facts that changed the plan

* All six Java services are **Spring Boot 4.0.7 / Spring Framework 7 on Java 21** (Tomcat 11, Jackson 3). The
  OpenTelemetry Java agent changelog lists Spring Boot 4 / Spring Framework 7 support (2.2x line), so the pinned
  agent 2.31.1 is expected to work; this had to be verified at runtime rather than assumed.
* `credit_card_meltdown`: `OrderController.getLatestStatus` evaluates the flag on **every request** (OpenFeature
  provider calls feature-flag-service over HTTP, no cache), then divides by zero; the exception is logged with
  `logger.error("Exception occured", e)` and rethrown, so Spring answers HTTP 500. A DB connection is opened
  first (`dbHelper.getConnection()`), so the fault needs a healthy database.
* `db_not_responding`: `TradeRepositoryWithDbNotResponding.AddTrade` sets `trade.Id = -1` when the flag is on;
  `SaveChanges` then fails, `TradeServiceBase.SaveChangesOrRollback` logs `LogError("Error while saving changes")`
  and throws `DbException`, which `BrokerExceptionFilter` maps to **503**. The broker caches flag values for
  `FEATURE_FLAG_CACHE_DURATION_S` (default 60 s); the lab sets it to 5 s.
* **The broker never calls accountservice.** `AccountServiceConnector` is registered in DI but has no caller in
  this fork, so the "broker -> account" hop suggested by the task does not exist. Real app-to-app HTTP calls with
  official zero-code instrumentation on both ends are `accountservice (Java) -> manager (.NET)` (driven by
  `GET /accountservice/api/account/{id}`) and `engine (Java) -> broker (.NET)` (scheduled every minute). The
  suite verifies the first one. Broker -> pricing-service (Go) exists but the Go side is not instrumented.
* Broker logging: `Program.cs` calls `builder.Logging.ClearProviders()` then `AddCustomLogger(...)`; the custom
  logger writes to the console only. Whether the OTel .NET ILogger bridge survives `ClearProviders()` had to be
  tested (see section 4).
* `calculationservice` (C++) links the Dynatrace OneAgent SDK for C; without a OneAgent the SDK is a no-op. There
  is no official OpenTelemetry zero-code instrumentation for C++, so it stays an explicit gap.
* `frontendreverseproxy` nginx config references OneAgent variables (`$dt_trace_id` ...) but declares them with
  `set`, so nginx starts without OneAgent (verified with `nginx -t`). The proxy is not instrumented in this
  milestone.
* `problem-operator` is Kubernetes-only and is not part of Compose; `loadgen` drives headless Chrome and is an
  opt-in profile here.

## 2. Design decisions

* Instrumentation is injected purely by **startup configuration**: the pinned official agents are downloaded
  once (`scripts/fetch-agents.sh`, SHA-256 verified) into `otel-lab/agents/` (git-ignored) and bind-mounted
  read-only into the unchanged application images. No business code is changed; images are built from the
  upstream Dockerfiles of this checkout and tagged `easytrade-otel-lab/<service>:<git-sha>`.
* Compose: `compose.dev.yaml` (upstream, builds from source) + overlay `otel-lab/compose.otel.yaml`, project name
  `easytrade-otel-lab`. Only the proxy is published, on `127.0.0.1:8080`. `!reset`/`!override` tags remove the
  upstream host port mappings and the frontend dev-server volume.
* Secrets: `~/.config/easytrade-otel-lab/otel.env` (0600, generated by `scripts/gen-runtime-env.sh`, outside the
  checkout) holds `OTEL_EXPORTER_OTLP_ENDPOINT` and `OTEL_EXPORTER_OTLP_HEADERS=Authorization=Bearer ...` and is
  attached via `env_file`. dtctl reads the token through an env placeholder in its config
  (`token: ${EASYTRADE_OTEL_LAB_DT_TOKEN}`) that `scripts/dtctl-lab.sh` fills from the token file.
* Export: direct OTLP/HTTP protobuf to `https://ybe54905.live.dynatrace.com/api/v2/otlp` (no Collector), traces +
  logs only (`OTEL_METRICS_EXPORTER=none`, `.NET: OTEL_DOTNET_AUTO_METRICS_ENABLED=false`), sampler `always_on`.
* Identity: `OTEL_SERVICE_NAME=<compose service name>`, resource attributes
  `service.namespace=easytrade-otel-lab`, `deployment.environment.name=easytrade-otel-lab`,
  `service.version=<image tag>`.
* Run isolation: the suite sends `X-Lab-Run-Id` / `X-Lab-Case` headers and the agents are configured to capture
  them as span attributes; results are still primarily selected by explicit UTC windows, and the attribute-based
  count is reported separately so that a header that does not reach telemetry is visible.
* Host memory: 7.6 GiB with ~2.5 GiB already in use is tight for MSSQL + 6 JVMs + 3 .NET + Node/Go/C++
  containers. Mitigations: JVM `-Xmx256m`, `MSSQL_MEMORY_LIMIT_MB=1536`, a 4 GiB swap file added to the host
  (`/swapfile`, persisted in `/etc/fstab`; remove with `swapoff /swapfile && rm /swapfile` + fstab edit).

## 3. Pre-flight checks that passed before any application telemetry existed

* `dtctl 0.39.0` installed from the GitHub release (SHA-256 verified against `checksums.txt`). `dtctl doctor`
  authenticates with the platform token; `fetch spans` / `fetch logs` queries succeed (empty, tenant quiet), so
  `storage:spans:read` and `storage:logs:read` are effective. `fetch dt.system.buckets` shows `default_logs`

## 4. Runtime findings

(filled in below as the deployment progressed)

### 4.1 First start (08:08-08:12)

* Build of all 17 images from source took ~15 min (Gradle x6, .NET x3, Go x2, Node, C++ with AMQP-CPP + OneAgent SDK
  download, MSSQL 2.2 GB pull). Peak memory during the build pushed the host into the new swap.
* **Node preload failed** (`offerservice` crash-looping): `--require /otel/node/node_modules/@opentelemetry/auto-instrumentations-node/register`
  is treated as a file path and bypasses the package `exports` map. Fix (config only): `NODE_PATH=/otel/node/node_modules`
  plus the bare specifier `--require @opentelemetry/auto-instrumentations-node/register`. The proxy crash-looped
  only because nginx could not resolve the `offerservice` upstream while it was down; it recovered by itself.
* Java agent 2.31.1 started in every JVM (`opentelemetry-javaagent - version: 2.31.1`), no agent warnings/errors
  in any Java container; Spring Boot 4 / Tomcat 11 server spans and `java.net.http` client spans are produced.
* .NET automatic instrumentation 1.16.0 (linux-musl-x64) initialised the CLR profiler and the tracer in all three
  Alpine containers; export log shows `Export succeeded for .../v1/traces`.
* All readiness probes passed ~2 min after `up` (MSSQL seeding is the long pole).
* First DQL inventory (window 08:10-08:13 UTC) returned spans from accountservice, broker-service, contentcreator,
  credit-card-order-service, feature-flag-service, loginservice, manager, offerservice; engine and
  third-party-service appeared in a wider window (their traffic is scheduler-driven). Logs arrived from all Java
  services and from offerservice (winston via `@opentelemetry/winston-transport`), with `trace_id`/`span_id`
  populated on request-scoped records.
* Stored identity fields as observed (spans): `service.name`, `service.namespace`, `deployment.environment.name`,
  `service.version`, `telemetry.sdk.language`, and Dynatrace-derived `dt.entity.service` / `dt.smartscape.service`
  (one entity per service name; Dynatrace created OpenTelemetry service entities without OneAgent).
  Logs carry the same resource fields plus `dt.entity.service` and `loglevel`/`status`, `content`,
  `trace_id`, `span_id`, `otel.scope.name` (the logger name).
* The `X-Lab-Run-Id` header is stored on Java server spans as `http.request.header.x-lab-run-id` (array value).
* Fixture correction: this fork's `POST /broker-service/v1/balance/{id}/deposit` requires card fields
  (`DepositMoneyDTO`), otherwise 400; the suite sends them.

### 4.2 .NET logs missing (08:12-08:20) - root cause and fix

* Symptom: zero log records from broker-service, manager and loginservice although all three print application
  logs at Information to the console; the instrumentation's own log said `Logs: Loaded AddOpenTelemetry from
  LoggingBuilder` and no `/v1/logs` export was ever attempted. Switching a throwaway manager to
  `OTEL_LOGS_EXPORTER=console` printed nothing either, so records never reached the OpenTelemetry provider.
* Ruled out: assembly version split (the profiler redirects all `Microsoft.Extensions.*` 8.0 references to the
  9.0 copies it ships, consistently), the `ASPNETCORE_HOSTINGSTARTUPASSEMBLIES` bootstrap path (same result),
  exporter/auth problems (traces export fine with the same settings).
* Root cause: the bridge is registered as an `ILoggerProvider` service when `LoggingBuilder` is constructed, i.e.
  before user code. **All three .NET services then call `ClearProviders()`** - broker in `Program.cs`, manager and
  loginservice inside `services.AddLogging(...)` in `Startup.cs` - which removes every `ILoggerProvider`
  registration including the injected one. No environment variable can undo that.
* Fix (targeted source change, commit "otel-lab: keep injected ILogger providers in .NET services"): replace
  `ClearProviders()` with a loop that removes only providers whose implementation type lives in the
  `Microsoft.Extensions.Logging.*` namespaces (Console/Debug/EventSource). The apps' own console providers are
  re-added by their existing code, so console output is unchanged; the OpenTelemetry provider survives.
  This is the "logging bridge/provider change" the task allows when configuration alone does not suffice.

### 4.3 Restart on the fixed images (08:19-08:21)

* `lab.sh build` (fully cached) + `lab.sh up` recreated all containers under the new tag `65bf1f366e28`; readiness
  took ~90 s (the proxy answered 502 for feature-flag-service until the JVM was up).
* Within a minute, stored logs from broker-service, loginservice and manager appeared
  (`telemetry.sdk.language == "dotnet"`), request-scoped ones with `trace_id`/`span_id`; console output unchanged.

* The captured header attribute is stored as an **array** on Java spans (`["run-..."]`) and as a **string** on

* The .NET `BrokerExceptionFilter` logs the handled 503 at Information; the ERROR records come from
  `TradeServiceBase.SaveChangesOrRollback` and from EF Core's own logger, both existing loggers, not fabricated.

## 7. Known gaps and non-standard points (candid list)

* Go services (pricing-service, aggregator-service) are not instrumented. The official Go zero-code path is the
  eBPF agent (`opentelemetry-go-instrumentation` v0.24.0), which needs a privileged sidecar sharing the target's
  PID namespace; it was not attempted within this milestone. Broker -> pricing-service therefore shows a CLIENT
  span without a matching SERVER span.
* calculationservice (C++ + OneAgent SDK) has no official OTel zero-code option; the SDK stays linked but inert.
* nginx reverse proxy and the static frontend are uninstrumented; traces start at the first instrumented service
  (the proxy forwards but does not create `traceparent`).
* The .NET fix is a source change in three files (provider cleanup instead of `ClearProviders()`); everything else
  is configuration and bind-mounted agents.
* Java scheduler traffic (card/third-party) cannot be paused without a restart; it is confined to other routes.
* The stored `service.version` equals the image tag (git revision of `src/`), which is a lab convention.
* Metrics are deliberately not exported (scope not requested); the empty-payload probe returned 200 on
  `/v1/metrics`, which says nothing about the metrics ingest scope.
